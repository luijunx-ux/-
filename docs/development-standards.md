# 开发规范

## 1. 基本原则

- 采用模块化、分层和依赖倒置设计，领域逻辑不直接依赖框架或外部服务。
- 配置与代码分离；敏感信息不得进入版本库、日志、测试快照或示例数据。
- 健康、节律与 AI 建议必须清晰标注适用边界，不替代医疗诊断。
- 涉及出生信息和位置的数据按敏感个人信息处理，遵循最小采集、最小留存与可删除原则。

## 2. 分支与提交

- 默认分支：`main`。
- 功能分支：`feature/<topic>`；修复分支：`fix/<topic>`；维护分支：`chore/<topic>`。
- 提交遵循 Conventional Commits：`feat:`、`fix:`、`docs:`、`test:`、`refactor:`、`chore:`、`ci:`。
- 一个提交只表达一个完整意图；合并前必须通过格式化、静态检查和测试。

## 3. Python / FastAPI

- 使用受支持的稳定版 Python；后续在 `backend/pyproject.toml` 锁定具体版本与工具。
- 代码使用类型标注；接口输入输出必须使用显式 Schema，不直接暴露 ORM 模型。
- 推荐分层：API → Application/Service → Domain → Repository/Infrastructure。
- 格式化与静态检查统一采用 Ruff；类型检查采用 mypy；测试采用 pytest。
- 异步边界必须明确，禁止在异步请求链中执行阻塞 I/O。

## 4. Flutter / Dart

- 遵循 Dart 官方分析规则，后续通过 `analysis_options.yaml` 固化。
- UI、状态管理、领域模型和数据访问分层；Widget 不承载业务规则。
- 所有用户可见文本集中管理，为国际化预留接口。
- 单元、Widget 与集成测试分别组织，关键流程必须具备自动化测试。

## 5. 数据库

- PostgreSQL Schema 变更必须通过可审查的迁移文件完成，禁止手工修改生产结构。
- 时间统一以 UTC 存储，展示时依据用户时区转换；出生地保留标准化位置与时区来源。
- 表与字段使用 `snake_case`；主键、创建时间、更新时间和必要审计字段保持一致。
- 日志与分析数据不得记录完整出生信息、精确位置、访问令牌或模型密钥。

## 6. AI、Agent 与 RAG

- Prompt、知识源、检索配置和评测集必须版本化。
- 模型输出视为不可信输入：进行结构校验、内容安全检查并提供降级路径。
- 生成内容应记录模型、Prompt 版本和必要追踪信息，但不得泄露隐私或密钥。
- 对计算型结果采用确定性程序实现与测试；LLM 负责解释和表达，不替代可验证计算。

## 7. API 与错误处理

- API 采用版本前缀，例如 `/api/v1`；契约变更优先保持向后兼容。
- 使用统一错误结构与机器可读错误码；不得把内部堆栈返回给客户端。
- 外部调用设置超时、有限重试和可观测性；非幂等请求不得盲目重试。

## 8. 测试与质量门禁

- 新增逻辑必须同时新增相应测试；缺陷修复必须包含回归测试。
- 合并门禁至少包含：格式化、静态检查、类型检查、单元测试、敏感信息扫描。
- 测试数据必须匿名或合成，不使用真实用户资料。

## 9. 文档与评审

- 架构决策写入 `docs/architecture/`；API 契约写入 `docs/api/`。
- 重要业务定义、历法/时区依据和算法版本必须注明来源与适用范围。
- Pull Request 描述需包含背景、变更、验证方式、风险和回滚策略。
